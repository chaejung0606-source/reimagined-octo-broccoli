# 05. 구현 노트 — 무엇이 되고 무엇이 안 되는가

1~3단계(문서 분류 → L0 → L1 → L2)를 OCR 없이 구현했습니다.
이 문서는 **설계(02·03·04번 문서)에서 실제로 달라진 것**과 **아직 못 하는 것**을 적어 둡니다.

---

## 1. 지금 동작하는 범위

| 층위 | 규칙 수 | 상태 |
|---|---|---|
| L0 서류 완비성 | 7 | ✅ 전부 동작 |
| L1 문서 내부 | 30 | ✅ 텍스트 레이어 기준 동작 (서명·스캔 품질 3건은 4단계) |
| L2 문서 간 교차 | 39 | ✅ 동작 (동승 중복 1건은 5단계 묶음 모드) |
| L3 규정·한도 | 11 | ⚪ 지침 수치를 넣으면 자동 활성 |

```bash
python -m app review 서류폴더 --type 출장비
python -m app rules --type 출장비        # 어느 규칙이 켜져 있는지 확인
```

### 이번 단계에서 판정하지 않는 검사

조용히 통과시키지 않고 **⚪ 이번 단계 미지원**으로 사유와 함께 남깁니다.
무엇을 아직 못 보고 있는지가 결과에 남아야 담당자가 직접 확인할 수 있습니다.

| 규칙 | 사유 |
|---|---|
| R-CMN-010 서명·날인 누락 | 서명란 영역 픽셀 판정 필요 (4단계) |
| R-CMN-014 신분증 주민번호 마스킹 | 신분증 사본 Vision 판독 필요 (4단계) |
| R-SCH-007 근무일지 결재란 서명 | 위와 같음 |
| R-TRV-020 동승 중복 청구 | 여러 사람을 함께 넣는 묶음 모드 필요 (5단계) |
| R-CMN-018 스캔 판독 불가 | 해상도·기울기 측정은 4단계. **텍스트 레이어가 없는 서류 목록은 지금도 알려줍니다.** |

## 2. 설계에서 바꾼 것

### 2-1. `공란`과 `미추출`을 필드 수준에서 구분

02번 문서는 "requires 필드가 하나라도 추출 실패면 REVIEW 강등"이라고 했습니다.
그대로 하면 **`총 이동경로` 칸이 비어 있는 것(🔴 이어야 함)** 과
**스캔이라 못 읽은 것(🔵 이어야 함)** 이 같은 결과가 됩니다.

그래서 필드에 상태를 셋 뒀습니다.

| 상태 | 뜻 | 규칙에서의 처리 |
|---|---|---|
| `PRESENT` | 값을 읽었다 | 그대로 평가 |
| `BLANK` | 칸은 찾았고 비어 있다 | **평가한다** → 대개 위반(🔴) |
| `MISSING` | 칸 자체를 못 찾았다 | 판정 보류(🔵) |

이 구분이 앱의 신뢰도를 좌우합니다. 샘플의 이성재·이동재 건이 정확히 이 경우입니다.

### 2-2. R-TRV-011(영수증 기간 이탈)을 표현식에서 검사기로

원래 정의는 `period.start <= receipt.datetime <= period.end` 였습니다.
그런데 샘플에는 성격이 다른 두 가지가 섞여 있습니다.

- **이동재**: 출장 종료 `7/3 12:00`, 귀로 통행료 `7/3 13:20` → **출장기간 기재가 틀린 것**
- **이성재**: 하이패스 8건 중 5건이 `6/20`·`6/24`·`7/5` → **다른 건의 영수증이 섞인 것**
  (기간 내 3건 8,500원이 기재액과 정확히 일치하므로 정산 자체는 정상)

둘을 한 규칙으로 ERROR 처리하면 이성재가 통째로 오탐이 됩니다. 그래서
`receipts_within_period` 검사기로 바꾸고 **출장 경계로부터의 거리**로 갈랐습니다.

| 조건 | 판정 | 조치 문구 |
|---|---|---|
| 경계에서 24시간 이내 (`near_boundary_hours`) | 🔴 | 출장기간을 정정하거나 해당 영수증을 제외 |
| 그보다 멀리 떨어짐 | 🟡 | 다른 건의 영수증이 섞였는지 확인 |

임계값은 `params.near_boundary_hours` 로 조정합니다.

### 2-3. R-TRV-010(영수증 내부 합계)도 검사기로

하이패스 영수증의 `총 8건 / 합계 33,900원` 은 **문서 전체**의 합계입니다.
이걸 영수증마다 비교하면 8건 전부 오탐이 납니다. `receipt_totals_match` 검사기가
나열형(문서 단위)과 전표형(품목 단위)을 나눠서 봅니다.

### 2-4. 규칙에 `only_subtypes` / `applies_to` 추가

TA형에는 근무일지·청구서·활동보고서가 아예 없습니다. 그런데 규칙은 그걸 찾으므로
없는 서류에 대한 🔵 판독 불가가 6건 쌓입니다. 실제로는 **그 서류가 필요 없는 것**입니다.

```yaml
  - id: R-SCH-006
    layer: L1
    only_subtypes: [SUPPORTERS]     # 서포터즈형에만 적용
```

같은 이유로 출장비에는 통장 사본·재학증명서·지급내역·개인정보 동의서가 없으므로
공통 규칙 8건에 `applies_to: [근로장학금, 혁신인재지원금]` 을 붙였습니다.
(R-CMN-017 작성일 규칙도 제외했습니다 — **출장신청서는 출장 전에 쓰는 문서**라
활동 종료일보다 앞서는 것이 정상입니다.)

### 2-5. 반복 규칙의 🔵 결과를 접는다

영수증이 9건이면 "가맹점 소재지를 읽지 못했습니다"가 9번 뜹니다.
사유가 같은 🔵/🟢 는 한 줄로 접고 건수만 남깁니다. 🔴/🟡 은 각각 고쳐야 할 항목이므로 접지 않습니다.

### 2-6. 메시지 템플릿 3곳 수정

`{allowed}` `{computed_days}` `{weekday}` 는 엔진이 채울 근거가 없어 `?` 로 나왔습니다.
템플릿이 표현식을 그대로 쓸 수 있으므로 자기 완결적으로 고쳤습니다.

```yaml
# 전: {subtype} 기준단가({allowed})
# 후: {subtype} 기준단가({settings.unit_price_table[subtype]})
```

## 3. 구현하면서 드러난 함정

실제 서류에서 반복될 것들이라 적어 둡니다. 전부 테스트로 고정해 두었습니다.

| 함정 | 증상 | 대응 |
|---|---|---|
| 표 머리행을 값으로 읽음 | `성명 직급 출장기간 …` → 성명이 `직급출장기간` | 열 이름이 3개 이상 모인 줄은 머리행으로 보고 건너뜀 |
| 라벨이 다른 단어에 박혀 있음 | `학점/구분 : 3학점 전공선택` → 학과가 `선택` | 라벨은 줄 첫머리·셀 경계에서만 인정 |
| 계좌번호를 주민번호로 오인 | 14자리 `59220101565992` 에서 13자리를 떼어 감 | 숫자 경계(`(?<!\d)…(?!\d)`) 강제 |
| 학번을 연도로 오인 | `202033445` → 연도 2020 → 활동일이 6년 전으로 | 연도는 `2026년` / `2026-05-06` 같은 **연도 자리**에서만 |
| 붙임 목록이 지문을 오염 | 서류 끝의 `붙임 1. 동의서 2. 재학증명서 …` 로 교차 오분류 | 지문 매칭 전에 붙임 목록 절단 |
| 종료일이 기간 밖으로 밀림 | 근로기간 `~3.31`(00:00)과 근로일 `3/31`(date) 비교 | 시각 없는 기간은 date 로 두고, 섞이면 날짜 기준 비교 |
| 목록이 Namespace 로 바뀜 | `transport_receipts` 와 `transport_receipts.parsed` 충돌 | 필드 이름 분리 + 얕은 경로 우선 |
| 데이터가 메서드에 가려짐 | `receipt.items` 가 `Namespace.items` 메서드를 돌려줌 | 담긴 값이 항상 이기도록 |
| 유령 영수증 | 출장증빙 서식의 체류 날짜를 영수증으로 착각 | 금액을 못 읽은 건은 영수증으로 세우지 않음 |
| 연번을 금액으로 오인 | 지급내역 `1 권석재 …` → 근로시간 1시간 | 행 맨 앞 1~3자리 숫자는 연번으로 제거 |

## 4. 아직 검증되지 않은 것 — **실제 서식 대조**

가장 중요한 남은 일입니다.

추출 패턴은 `docs/01-sample-analysis.md` 에 기록된 **구조와 수치**를 보고 썼습니다.
실제 PDF 의 글자 배치·줄바꿈까지 같다는 보장은 없습니다. 회귀 테스트가 통과한다고
실제 파일에서 추출된다는 뜻이 아닙니다. (샘플은 개인정보 때문에 저장소에 없습니다.)

맞추는 방법은 간단합니다.

```bash
# 1. 실제 파일에서 어떻게 뽑히는지 본다
python -m app dump 실제서류폴더

# 2. 분류가 맞는지 본다
python -m app classify 실제서류폴더 --type 출장비

# 3. 검토를 돌려 🔵 판독 불가가 어디서 나는지 본다
python -m app review 실제서류폴더 --type 출장비
```

🔵 가 뜨는 필드의 라벨을 `app/extract/*.py` 의 `_*_LABELS` 목록에 추가하면 됩니다.
대부분 라벨 표기가 한두 개 다른 정도일 것입니다.

실제 서식 한 벌만 주시면 이 작업은 금방 끝납니다.

## 5. 4단계(OCR·Vision)를 붙일 자리

추출기는 이미 갈라져 있어서, 4단계는 **필드를 더 채우기만** 하면 됩니다.
규칙과 엔진은 손대지 않습니다.

```python
# app/extract/<새 모듈>.py
bag.put("worklog.rows", rows, confidence=Confidence.VISION_HANDWRITE)  # 0.60
```

신뢰도를 `VISION_HANDWRITE`(0.60)로 기록하면 엔진이 자동으로 🔵 판독 불가로 올리고
원본과 나란히 확인하게 합니다. 손글씨를 읽었다고 바로 반려시키지 않는 것이 핵심입니다.

채워야 할 주요 필드:

| 필드 | 출처 | 규칙 |
|---|---|---|
| `worklog_handwrite.rows[]` | 손글씨 근무일지 | R-SCH-001~006 |
| `bankbook.holder` / `.account_no` | 통장 사본 | R-CMN-015/016 |
| `enrollment_cert.issued_at` | 재학증명서 | R-CMN-013 |
| `receipts[].merchant_address` / `.items[]` | 체류 영수증 스캔 | R-TRV-013/023/024 |
| `trip_evidence.map_distance` | 지도 캡처 | R-TRV-007 |
| 서명란 존재 여부 | 전 서류 | R-CMN-010, R-SCH-007 |
